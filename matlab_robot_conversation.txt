Yes. If you already have a working controller, a practical starting point is imitation learning: train a neural network to reproduce that controller's commands, then evaluate it controlling the robot in simulation.

For a robot arm, the mapping could be:
[q, qDot, qDesired, qDotDesired] -> joint torques

The inputs must contain enough information to determine the command. If your controller uses integral error, previous commands, or internal state, include that information or use a network with memory.

A MATLAB workflow is:
1. Collect examples from the existing controller. Run varied trajectories, initial conditions, payloads, and disturbances. Record the controller inputs and corresponding commands at the intended control sample time.
2. Split by complete simulation runs. Keep separate trajectories for training, validation, and testing. Randomly splitting neighboring time samples can make accuracy look better than it is.
3. Train a regression network. For fixed-size numeric inputs and torque outputs, fitrnet is a straightforward starting point.
4. Evaluate the network in closed loop. Replace the controller in simulation and measure tracking error, overshoot, actuator saturation, disturbance recovery, and execution time. Accurate command predictions alone do not establish closed-loop stability.
5. Integrate it with the robot. Apply the same preprocessing at runtime, enforce actuator limits, and retain the original controller as a fallback during initial trials.

For MATLAB R2024b or later, this illustrates training a network with multiple torque outputs using Statistics and Machine Learning Toolbox:

% Each row is one control sample.
% XTrain: [q, qDot, qDesired, qDotDesired]
% UTrain: joint torque commands from the existing controller
% XTest and UTest come from separate held-out trajectories.

% Normalize targets using training data only.
torqueMean = mean(UTrain,1);
torqueScale = std(UTrain,0,1);
torqueScale(torqueScale < 1e-8) = 1;

normalizedTorques = (UTrain - torqueMean)./torqueScale;

controllerNet = fitrnet(XTrain, normalizedTorques, ...
    LayerSizes=[64 64], ...
    Standardize=true);

% Predict held-out commands and restore physical units.
predictedTorques = predict(controllerNet,XTest) ...
    .*torqueScale + torqueMean;

torqueRMSE = sqrt(mean((predictedTorques - UTest).^2,1))

save("learnedController.mat", ...
    "controllerNet","torqueMean","torqueScale")

In Simulink, you can use the RegressionNeuralNetwork Predict block, followed by the torque scaling and actuator limits. For recurrent networks or custom training losses, use Deep Learning Toolbox with trainnet and dlnetwork.

If you do not have a controller to imitate, reinforcement learning is another route: train against a robot simulation with a reward for tracking and penalties for excessive effort or constraint violations. That requires Reinforcement Learning Toolbox and a suitable simulation environment.

For a mobile robot, start by training a network to imitate a path-following controller. The network receives tracking errors and robot motion, then outputs steering and velocity commands.

The steering representation depends on the robot:
- Car-like robot: steering angle and forward velocity.
- Differential-drive robot: angular velocity and forward velocity.

A useful starting set of inputs is:

X = [crossTrackError, headingError, measuredVelocity, ...
     pathCurvature, desiredVelocity];

The targets are the existing controller's commands:

U = [steeringCommand, velocityCommand];

For heading error, using sin(headingError) and cos(headingError) instead of the raw angle avoids the discontinuity at +/- pi. Include additional inputs if the controller uses look-ahead geometry, past commands, or internal state.

The MATLAB workflow would be:
1. Build a simulated robot and baseline controller. Pure pursuit is a common starting point for path following, paired with a velocity controller.
2. Generate training runs. Vary paths, curve sharpness, desired speeds, initial position and heading errors, and disturbances. Record synchronized inputs and commands at each controller update.
3. Train the network. Use fitrnet for a small network with fixed-size inputs. Normalize both command outputs so their different units do not skew training.
4. Test on entirely new paths in closed loop. Compare tracking error, completion rate, command smoothness, and inference time against the baseline.
5. Improve coverage. If the learned controller drifts into unfamiliar states, collect the baseline controller's commands at those states in simulation and retrain.

The resulting control loop is:

Path + estimated robot state
             |
             v
      Compute tracking inputs
             |
             v
        Neural network
             |
             v
   Command limits and rate limits
             |
             v
         Mobile robot

Keep obstacle avoidance and emergency stopping as explicit parts of the control system unless you deliberately include them in the learned controller's scope. A network trained only on path-following examples has not learned obstacle avoidance.

Also clarify what "velocity command" means: if it is a requested speed sent to an existing motor controller, the network replaces the navigation controller. If you want it to command motor effort directly, that is a different training problem.

The TurtleBot3 Burger is a differential-drive robot. Your neural controller would output:
- Forward velocity v, in m/s.
- Angular velocity omega, in rad/s.

It turns by driving its two wheels at different speeds.

For a first MATLAB demo, I recommend replacing a path-following controller, while retaining the robot's existing motor control. A useful network mapping is:

% One row per control sample
X = [crossTrackError, sin(headingError), cos(headingError), ...
     measuredForwardVelocity, measuredAngularVelocity, ...
     pathCurvature, desiredForwardVelocity];

U = [commandedForwardVelocity, commandedAngularVelocity];

Train it using examples from a pure-pursuit controller and a speed policy. Collect runs with straight paths, curves, different speeds, and varied starting positions. Reserve entire paths for testing, then compare the learned controller with the original in closed-loop simulation.

For ROS 2 integration, the usual connections are:
- /odom: receive estimated position, heading, and velocity.
- /cmd_vel: publish forward and angular velocity commands.
- /scan: receive lidar data for obstacle detection.

Verify the actual topic names and message types on your robot. With a geometry_msgs/Twist command interface, MATLAB would publish:

node = ros2node('/matlab_controller', 42); % Match the robot's domain
pub = ros2publisher(node, '/cmd_vel', 'geometry_msgs/Twist');
msg = ros2message(pub);

% vCommand and omegaCommand come from the trained controller.
msg.linear.x = vCommand;
msg.angular.z = omegaCommand;
send(pub, msg);

Apply speed limits and acceleration limits before publishing. Keep obstacle stopping separate for the first demo: these tracking inputs do not teach the network to avoid obstacles.

You can begin entirely in MATLAB simulation without ROS 2 installed. Build a differential-drive simulation, generate controller examples, train the network, and compare its path tracking. ROS 2 becomes relevant when you connect the trained controller to the actual TurtleBot.
